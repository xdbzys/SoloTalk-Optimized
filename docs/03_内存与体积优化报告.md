# 内存与体积优化报告

> 数据来自对 `SoloTalk_v2.2.apk` 的**真实解析**，非估算。
> 原始快照见 `report/apk_analysis.json`，复现脚本 `tools/analyze_apk.py`。

## 一、测量方法

APK 共 **235,045,570 字节**（235.05 MB / 224.16 MiB），完整下载在受限网络下超时。
由于 APK 本质是 ZIP，只需取文件末尾 256 KB 即可读到 **EOCD + 完整中央目录（794 个条目）**，
从而精确得到每个条目的压缩/未压缩大小 —— 体积诊断所需的全部信息，无需下载整包。

```
python3 tools/analyze_apk.py --tail <末尾片段> --total 235045570 --json report/apk_analysis.json
```

> 下文统一用 **MiB（1 MiB = 1,048,576 字节）**，与工具输出一致；
> 用户看到的「235 MB」是十进制 MB，两者指同一个包。

## 三、运行时内存为什么大

| 常驻项 | 估算内存 | 依据 |
|---|---:|---|
| BGE `bge-small-en-v1.5` ONNX 模型 + ONNX Runtime 工作集 | 约 100–130 MB | 32.44 MiB 模型文件 + 推理会话/中间张量，通常为文件体积 3–4 倍 |
| Vosk 解码图（`Gr.fst` 22.90 + `HCLr.fst` 21.38 + `final.mdl` 15.22 + ivector 7.90） | 约 150–200 MB | Kaldi FST 展开后常为文件体积 2–3 倍 |
| 4 份 native so 同时映射、9 个 dex、录音 PCM 缓冲、图片 | 数十 MB | — |
| **合计** | **约 250–350 MB** | 低端机易 OOM |

这正好解释原 README 的自述：

> 「手机版批改与历史记录功能尚不稳定，可能无法批改与回放录音，请做好预期」

另外两处代码级问题：

1. **原 `evaluate_recordings` 每次批改都 `_get_bge_model()` 懒加载模型**，模型常驻不释放；
2. **原 `_open_package_zip()` 直接 `zf.extractall(temp_dir)`**，把整个题目包（可能含几十~几百 MB 视频）
   一次性解压到磁盘，且 `tempfile.mkdtemp()` 建的目录不随用随清 —— 存储与内存双峰值。

## 四、优化措施

### A. 已落地（本次交付的代码直接生效）

| # | 措施 | 落地位置 | 效果 |
|---|---|---|---|
| A1 | **停用 BGE / ONNX 模型**，`_get_bge_model()` 直接返回 `None`；评分改用零模型多维算法 | `app/SoloTalk_optimized.py`、`scoring/gd_celst.py`、`android/GdCelstScoring.kt` | 消除 32.66 MiB 模型文件 + 62.29 MiB `libonnxruntime*.so` + 100–130 MB 常驻内存 |
| A2 | **题库按需加载**：只读索引；选中才从 ZIP 流式读 `data.json`；只解压确需媒体，设单文件 32 MB / 累计 64 MB 上限；`TemporaryDirectory` 用完即清 | `scoring/question_bank.py`、`app/SoloTalk_optimized.py` 的 `_open_package_zip()`、`android/SoloTalkScoringBridge.kt` | 消除 `extractall` 的整包解压峰值与临时文件堆积 |
| A3 | **音频流式识别**：4000 帧循环读，不整段载入；录音 PCM 不复制整份 | `scoring/asr_provider.py` `OfflineASRProvider` | 识别阶段内存恒定 |
| A4 | **题库纯文本、不内置音视频**：第二轮 18 套共 **约 518 KB**（17 套纯文本由 TTS 合成听力；仅用户上传原题保留 3 段真实 mp3 约 459 KB，且按需加载），ZIP 最高压缩 | `assets/question_bank/`、`tools/build_question_bank.py` | 内置资源几乎不占体积；含音频的单套仅在选中时解压对应条目 |
| A5 | **在线 ASR 优先 + 按需加载 Vosk**：联网时不加载本地声学模型；断网才加载，用完可释放 | `scoring/asr_provider.py` `AutoASRProvider` | 常态运行不再常驻 150–200 MB Vosk 工作集 |

### B. 需要安卓工程侧配合（提供配置，见 `android/README.md`）

| # | 措施 | 预计释放 |
|---|---|---:|
| B1 | **ABI 分包 / App Bundle**：只发 `arm64-v8a`（或 `arm64-v8a` + `armeabi-v7a`），去掉 `x86`/`x86_64`（仅模拟器用）与已废弃的 `mips`/`mips64`/`armeabi` | 75.38 MiB（仅 arm64）或 55.85 MiB（arm64+v7a） |
| B2 | **移除 `onnxruntime` 依赖与 `bge-model` assets**（A1 的工程侧动作） | 94.95 MiB |
| B3 | **Vosk 模型改为首次使用时按需下载**（不随包内置），或换 `vosk-model-small-en-us-0.15`；同时删除 `libvosk.so` 的非目标 ABI | 105.53 MiB |
| B4 | **R8 全量混淆 + 精简依赖**（9 个 dex 共 19.81 MiB，按行业常见 35% 缩减） | 6.93 MiB |
| B5 | **416 张 png → WebP**（`qq_group_qr.png` 单张 0.45 MiB 可优先转） | 0.52 MiB |

### C. 综合估算

> 计算已扣除 B1 与 B2/B3 中 `.so` 的重叠部分，避免重复计数。

| 项 | 值 |
|---|---:|
| 现 APK（压缩后） | 223.89 MiB |
| 预计释放 | **183.10 MiB** |
| **预计优化后 APK** | **约 40.79 MiB** |
| 缩减比例 | **约 82%** |
| 运行时常驻（评分相关） | 从 250–350 MB → **< 5 MB**（纯文本算法，常数级） |

若保守只做 B1（双 ABI）+ A1，不做 Vosk 按需下载，也能降到约 **85–95 MiB**，
且**不需要改动任何评分逻辑之外的业务流程**。

## 五、如何验证优化效果

```bash
# 1. 重新解析新 APK 的体积构成，与 report/apk_analysis.json 对比
python3 tools/analyze_apk.py --apk path/to/new.apk --json report/apk_after.json

# 2. 确认新包里不再出现模型与多余 ABI
python3 - <<'PY'
import json
d=json.load(open('report/apk_after.json'))
bad=[e['name'] for e in d['entries']
     if 'bge-model' in e['name'] or 'onnxruntime' in e['name']
     or e['name'].startswith(('lib/x86','lib/mips','lib/armeabi/'))]
print('应为空:', bad)
PY

# 3. 评分准确度不因瘦身退化
python3 tools/verify_scoring.py
python3 tools/verify_integration.py
```

## 六、诚实说明

- 上述 **40.79 MiB 是估算值**，真实值取决于最终保留哪些 ABI、是否保留离线 Vosk、
  以及 R8 对现有依赖的实际缩减率；必须重新打包后用 `analyze_apk.py` 实测确认。
- 本报告**没有重新打包 APK**（原因见 `04_现状核查与结论.md`：仓库无安卓源码、无签名私钥）。
  已提供的是可直接集成的 Kotlin 内核、Gradle 配置说明与精确的诊断数据。
- 若保留离线 Vosk 兜底，弱网/断网场景仍会加载一次模型；
  建议在 `onTrimMemory()` / 批改结束后显式释放，避免长驻。
